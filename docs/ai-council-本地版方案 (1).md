# AI Council 本地版 — 产品方案

> 给 Codex 的实现方案
> 定位：本地 Mac 上的多模型网页群聊工作台
> 技术栈：React + Vite + Tauri + macOS Chrome + AppleScript/JS 注入
> 幕后管家：DeepSeek API（额度管理、上下文压缩、防吵架、流程控制）

---

## 一、系统角色定义

整个系统有四种角色：

| 角色 | 说明 |
|------|------|
| **你（甲方）** | 唯一决策者，出题、拍板、改方向 |
| **讨论成员** | Claude / ChatGPT / Gemini 网页版，通过浏览器自动化交互 |
| **管家（DeepSeek API）** | 不参与讨论内容，负责：额度监控、上下文压缩、防吵架检测、转述编排 |
| **系统** | Tauri 本体，负责浏览器控制、消息流转、本地存储 |

铁律：**讨论成员之间永远不直接对话。** 所有消息都经过管家处理后，由系统转发到各网页线程。

---

## 二、核心流程

```
你出题
  ↓
系统把题目发给所有讨论成员（各自的网页线程）
  ↓
等所有成员回复（或超时跳过）
  ↓
停下来，展示所有回复给你看
  ↓
你说话（"继续" / 带反馈 / "终稿" / 撤回）
  ↓
管家根据你的指令 + 当前 transcript，生成下一轮要发给各成员的内容
  ↓
系统发送，循环
```

**绝对不自动进入下一轮。每轮结束必须等你说话。**

---

## 三、管家（DeepSeek）的五项职责

管家是整个系统的大脑，通过 DeepSeek API 调用实现。每一项职责对应一个独立的 API 调用，prompt 和输出格式固定。

### 3.1 转述编排

管家的核心工作。每轮你说完话后，管家负责生成要发给各成员的实际内容。

**输入：**
```json
{
  "topic": "讨论主题",
  "your_message": "你本轮说的话",
  "current_round": 3,
  "members": ["Claude", "ChatGPT", "Gemini"],
  "latest_replies": {
    "Claude": "Claude 上轮回复的摘要",
    "ChatGPT": "ChatGPT 上轮回复的摘要",
    "Gemini": "Gemini 上轮回复的摘要"
  }
}
```

**管家的 system prompt：**
```
你是一个讨论编排助手。你的工作是根据甲方的指令，生成要发给每个讨论成员的消息。

规则：
1. 每条消息必须以【讨论主题】开头，防止跑题
2. 消息要简短，突出重点，不要把所有历史都塞进去
3. 转述其他成员的观点时，只提关键结论，不复制原文
4. 如果甲方给了方向性反馈，必须放在最显眼的位置
5. 禁止在消息中引导成员互相反驳或争论
6. 每条消息控制在 500 字以内

输出 JSON 格式：
{
  "messages": {
    "Claude": "要发给 Claude 的内容",
    "ChatGPT": "要发给 ChatGPT 的内容",
    "Gemini": "要发给 Gemini 的内容"
  },
  "skip": ["如果有成员本轮不需要发言，列在这里"]
}
```

### 3.2 上下文压缩

每次收到成员回复后，管家负责把回复压缩成摘要，用于下一轮转述。

**管家的 system prompt：**
```
你是一个摘要助手。把以下 AI 回复压缩成 3 句话以内的核心要点。
只保留：关键结论、具体建议、与主题直接相关的内容。
去掉：客套话、重复内容、过渡句、"我认为"之类的废话。
如果回复中有具体数据或方案细节，优先保留。
```

**触发时机：** 每条成员回复到达后立即压缩。压缩后的摘要用于转述，原文保存在 transcript 中。

### 3.3 防吵架检测

管家检测成员回复中是否出现无意义的互相反驳。

**管家的 system prompt：**
```
你是一个讨论质量检测器。判断以下回复是否属于"无效争论"。

无效争论的特征：
- 纯粹否定对方，没有给出自己的替代方案
- 重复自己之前已经说过的观点
- 在细枝末节上纠缠，偏离主题
- 语气变得情绪化，开始"教训"对方

输出 JSON：
{
  "is_arguing": true/false,
  "reason": "简短说明",
  "suggestion": "如果在吵架，建议怎么处理"
}
```

**触发时机：** 每条成员回复到达后检测。如果检测为吵架：
1. 在界面上标注该回复为"⚠️ 疑似无效争论"
2. 下一轮转述时，管家自动忽略争论内容，只保留有建设性的部分
3. 如果连续 2 轮检测到同一个成员在吵架，建议你跳过该成员或更换话题

### 3.4 额度管理

管家通过 DeepSeek API 来实现额度监控逻辑。这不是去读各网站的额度页面，而是基于本地计数 + 规则推断。

**本地追踪的数据：**
```json
{
  "Claude": {
    "messages_sent_today": 15,
    "last_reset_time": "2026-05-12T00:00:00",
    "reset_interval_hours": 4,
    "estimated_limit": 40,
    "consecutive_failures": 0,
    "status": "healthy"
  },
  // ChatGPT, Gemini 同理
}
```

**额度推断规则：**
- 每次成功发送消息并收到回复：`messages_sent_today += 1`
- 每次发送失败或收到"限流/额度用尽"类错误：`consecutive_failures += 1`
- 连续失败 2 次：标记为 `rate_limited`，暂停该成员
- 定时检查重置：根据各平台已知的重置周期，自动判断何时恢复

**额度预警（管家判断）：**
```
你是额度管理助手。根据以下各成员的使用数据，判断：
1. 哪些成员接近额度上限（使用率 > 80%）
2. 哪些成员应该优先使用（余量最多）
3. 本次讨论预计还需要多少轮，额度是否够用
4. 如果额度紧张，建议怎么分配（比如只让 2 个成员参与，省 1 个的额度）

输出 JSON：
{
  "warnings": ["Claude 今日已用 35/40，建议控制发言轮数"],
  "recommended_order": ["Gemini", "ChatGPT", "Claude"],
  "suggestion": "建议本轮只发给 Gemini 和 ChatGPT，保留 Claude 额度用于终稿"
}
```

**界面显示：**
- 顶部成员条旁边显示各成员的额度进度条（估算值）
- 接近上限时变黄，触发限流时变红
- 点击可看详细数据和预计重置时间

### 3.5 讨论质量把控

管家在每轮结束后给你一个简短的讨论状态概览。

```
根据本轮各成员的回复，用 2 句话告诉甲方：
1. 这一轮有没有实质性进展（新观点、新方案、有价值的修改）
2. 你建议下一步怎么做（继续互评 / 该收尾了 / 某个成员的方向最好值得深入）
```

**显示在每轮分隔线上**，帮你快速判断要不要继续。

## 四、撤回与驳回

### 4.1 你说错了 — 撤回

- 你发出的每条消息右侧有「撤回」按钮
- 撤回后：
  1. 消息在 transcript 中标记为 `withdrawn`，灰色删除线
  2. 如果消息已经发给了模型，管家生成一条修正消息发给所有成员：
     "甲方修正了上一条指令，请忽略之前的内容。以下是新的指令：{你重新输入的内容}"
  3. 如果还在发送队列中，直接取消
- 撤回后 composer 自动填入原文，方便你修改后重发

### 4.2 模型说错了 — 驳回重做

- 每条模型回复右侧有「重做」按钮
- 点击后弹出小输入框，可选填驳回理由
- 管家向该模型生成重做消息：
  "你上一条回复不符合要求。{驳回理由}。请重新回答，注意聚焦主题。"
- 被驳回的回复在 transcript 中标记为 `rejected`，灰色显示
- 其他成员不需要知道

**消息气泡：**
- 你的消息靠右，模型消息靠左
- 每条模型消息显示：模型图标 + 名称 + 响应耗时
- 被驳回：灰色 + 删除线 + "已驳回"
- 被撤回：灰色 + 删除线 + "已撤回"
- 疑似吵架：黄色边框 + ⚠️ 标注
- 正在等待：显示"正在思考..."

**轮次分隔线：**
- 每轮之间一条线 + "第 N 轮"
- 分隔线下方显示管家的 2 句话讨论状态

**底部 Composer：**
- 左侧「继续」按钮 — 无额外指令直接下一轮
- 中间输入框 — 写反馈或新指令
- 右侧「终稿」按钮 — 进入收尾

- 横条显示每个成员 + 状态 + 额度进度条
- 🟢 就绪 / 🔄 回复中 / 🟡 额度紧张 / 🔴 已限流 / ⏸️ 已暂停
- 点击成员可：暂停/恢复、查看详细额度、打开该线程网页

### 5.3 终稿流程

1. 你点「终稿」
2. 弹出选择器：让谁写终稿？（管家会推荐余量最多的成员）
3. 可选补充终稿要求
4. 管家生成终稿 prompt，包含：主题 + 各轮关键摘要 + 你的终稿要求
5. 系统发给指定成员
6. 终稿回复高亮显示，标注"终稿"
7. 你可以：接受 / 要求修改 / 换人重写

## 六、上下文管理策略

核心原则：**发给模型的内容要短、要重点突出。** 不要把所有历史都塞进去。

### 6.1 每轮发给模型的内容结构

```
【讨论主题】{topic}（永远保留，不裁剪）

【甲方最新指令】{你本轮说的话}（永远保留）

【上轮要点】（管家压缩后的摘要，每个成员 2-3 句话）
- Claude 认为：xxx
- ChatGPT 认为：xxx
- Gemini 认为：xxx

【你的任务】{管家根据当前阶段生成的指令}
```

**硬性限制：** 发给每个模型的总内容不超过 800 字。超过则由管家进一步压缩上轮要点。

### 6.2 三层记忆

```
Transcript（原始层）
  → 每条消息原样保存
  → 字段：id, round, provider, content, timestamp, status, summary
  → 存储：IndexedDB

Working Context（工作层）
  → 管家每轮生成的压缩上下文
  → 不持久化，用完即弃
  → 控制在 800 字以内

Room Memory（长期层）
  → 每次讨论结束时，管家生成结构化总结
  → 存储：IndexedDB
  → 下次新讨论可引用
```

## 七、额度管理模块详细设计

### 7.1 数据模型

```typescript
interface QuotaTracker {
  provider: 'Claude' | 'ChatGPT' | 'Gemini';
  
  // 计数
  messages_sent_today: number;
  messages_sent_this_window: number;  // 当前重置窗口内
  
  // 重置
  reset_interval_hours: number;       // 各平台不同
  last_reset_time: string;            // ISO timestamp
  next_estimated_reset: string;       // 预估的下次重置时间
  
  // 限制（估算值，可手动调整）
  estimated_limit_per_window: number;
  
  // 状态
  consecutive_failures: number;
  last_failure_reason: string;
  status: 'healthy' | 'warning' | 'rate_limited' | 'error';
  
  // 历史
  daily_history: { date: string; total_sent: number; failures: number }[];
}
```

### 7.2 各平台默认配置

```json
{
  "Claude": {
    "reset_interval_hours": 4,
    "estimated_limit_per_window": 40,
    "notes": "Pro 订阅，每 4 小时重置，用量根据消息长度浮动"
  },
  "ChatGPT": {
    "reset_interval_hours": 3,
    "estimated_limit_per_window": 40,
    "notes": "Plus 订阅，GPT-4 有单独限额"
  },
  "Gemini": {
    "reset_interval_hours": 24,
    "estimated_limit_per_window": 50,
    "notes": "Advanced 订阅，日限额较高"
  }
}
```

这些数值是初始估算，**用户可以在设置中手动调整**。系统也会根据实际使用中的成功/失败率自动修正估算。

### 7.3 额度界面

**设置页 — 额度管理：**
- 每个成员一行：当前状态 + 本窗口已用/预估上限 + 下次重置时间
- 手动调整按钮：修改预估上限和重置间隔
- 历史图表：最近 7 天每日用量趋势
- 一键重置计数器（比如你手动去网页刷新了额度）

**主界面 — 实时状态：**
- 成员条上的进度条实时更新
- 低于 20% 余量时自动变黄 + 底部提示
- 触发限流时变红 + 弹出通知

## 八、防跑题 + 防吵架 + 省额度 的联动机制

这三个问题本质上是一个系统：**让每一条发出去的消息都有价值。**

管家在每轮做以下判断：

```
输入：当前 transcript、各成员最新回复、你的最新指令、各成员额度状态

判断：
1. 有没有人在跑题？→ 下轮转述时加强主题锚定
2. 有没有人在吵架？→ 下轮转述时忽略争论内容，只保留建设性部分
3. 额度还够几轮？→ 如果紧张，建议减少参与成员或直接进入终稿
4. 讨论有没有在推进？→ 如果连续 2 轮没有新观点，建议收尾

输出：
{
  "action": "continue" | "warn" | "suggest_finish",
  "members_to_send": ["Claude", "Gemini"],  // 可能跳过某些成员
  "warnings": ["ChatGPT 连续两轮在重复同一观点，建议跳过"],
  "quota_alert": "Claude 还剩约 5 条额度，建议留给终稿"
}
```

**这个判断在你说话之后、消息发出之前执行。** 如果有严重问题（比如额度已经用完），系统会在你点"继续"后弹出提示，让你确认或调整。

## 九、房间与存储

### 9.1 房间系统

```
Room
├── config（成员列表、各成员线程 URL、额度配置）
├── room_memory（历史讨论的结构化总结）
├── Session 1（已结束）
│   ├── topic
│   ├── transcript
│   ├── quota_log（本次讨论的额度消耗记录）
│   └── final_output（终稿）
├── Session 2（进行中）
│   ├── topic
│   └── transcript
```

### 9.2 存储方案

全部用 IndexedDB，不用 localStorage。

表结构：
- `rooms`：房间配置
- `sessions`：每次讨论
- `messages`：transcript 消息
- `quota_logs`：额度使用记录
- `room_memory`：长期记忆

支持：
- 导出房间为 JSON
- 导入房间 JSON
- 清除单个房间数据
- 清除所有数据

## 十、网页自动化层

### 10.1 发送流程

```
管家生成消息内容
  ↓
系统检查目标成员状态（healthy?）
  ↓
通过 AppleScript 激活 Chrome 对应标签页
  ↓
通过 JS 注入：找到输入框 → 填入内容 → 点击发送按钮
  ↓
记录发送时间，开始轮询等待回复
```

### 10.2 读取回复流程

```
发送后开始轮询
  ↓
前 10 秒：每 1 秒检查一次
10-60 秒：每 3 秒
60 秒以上：每 5 秒
  ↓
检测到新内容出现 → 切回每 1 秒
  ↓
连续 2 次内容 hash 一致 → 回复完成
  ↓
提取回复文本 → 发给管家压缩 → 存入 transcript
```

### 10.3 选择器容错

每个网站用优先级选择器链，主选择器失败时自动尝试备选。
连续失败 3 次主选择器但备选命中 → 提示"检测到网站可能更新"。

### 10.4 超时与降级

- 90 秒无回复 → 标记 timeout
- 你可选：重试 / 跳过本轮 / 手动检查
- 某成员连续失败 3 次 → 自动暂停，不阻塞其他成员

## 十一、实现优先级

### P0 — 核心跑通（先做这些）

1. **管家编排引擎** — DeepSeek API 调用链：转述生成 + 上下文压缩
2. **一轮一停的消息流** — 发题 → 收回复 → 停下等你 → 你说话 → 下一轮
3. **基本界面** — 消息流 + 轮次分隔 + composer（继续/输入/终稿）
4. **额度计数器** — 本地计数 + 成员条上的进度条

### P1 — 体验完整化

5. **撤回 + 驳回重做**
6. **防吵架检测 + 标注**
7. **管家的讨论质量概览**（每轮分隔线上的 2 句话）
8. **终稿流程**
9. **IndexedDB 持久化 + Session 概念**

### P2 — 稳定性

10. **自适应轮询 + 回复完整性检测**
11. **选择器容错链**
12. **额度自动修正**（根据实际成功/失败率调整估算值）
